# mdeck

A markdown-based presentation tool.

## Design Principles

- **Visual appeal is paramount.** Every rendered element (text, code, transitions, scroll effects) must look polished and professional. Prefer smooth animations over instant state changes.
- **Simplicity over complexity.** Fewer controls, fewer options, fewer edge cases. The tool should feel effortless to use. When in doubt, leave it out.
- **Any markdown file should be presentable.** Overflow handling, layout inference, and sensible defaults mean users shouldn't need to tailor their markdown to the tool.

## Layout

Rust workspace with two crates: `crates/mdeck` (package `mdeck`: a library, `mdeck::builtins` + `mdeck::run`, and the thin `mdeck` binary) and `crates/mdeck-sdk`, the public extension interfaces (`paint::Painter` and its own geometry types, tokens, content, stage, the `Engine`/`Visual`/`DesignSet`/`Transition` traits, the `Registry`, `testing`; no egui type in its surface, raw egui only behind `unstable-egui`). mdeck's built-in engines and visuals register through it like an extension's (see Library and registry, Engines); the SDK tutorial engines and the engine template are workspace members under `examples/`. `crates/mdeck/doc/mdeck-spec.md` is the format spec, embedded in the binary via `include_str!` and printed by `mdeck spec`. Visualization design rules and the docs that must stay in sync with visualizations live in `crates/mdeck/src/render/CLAUDE.md`.

## Key Patterns

- **Rendering:** Scale factor `min(w/1920, h/1080)` applied to all pixel sizes for resolution independence
- **Syntax highlighting:** `syntect` with `LazyLock`-cached `SyntaxSet` / `ThemeSet`; theme maps to syntect theme via `Theme::syntect_theme_name()`; highlighted `LayoutJob`s are cached per (code, language, size, theme)
- **PDF export:** `--format pdf` feeds the same rendered canvases to `export::pdf::PdfDoc` (Flate-compressed RGB image per page, 0.5 pt per px, outline entry per slide). `--notes` adds a second pass per slide that draws a portrait notes page in the light theme (`export::notes`), then composites the slide image into it; notes paginate by block, never shrink.
- **PNG export:** eframe (glow renderer) window with `pixels_per_point` forced to 1; the slide is rendered in window-sized tiles via `ViewportCommand::Screenshot` / `Event::Screenshot` and stitched, so output is exactly `--width`×`--height` on any display. The glow renderer is required: wgpu's screenshot readback is asynchronous and never completes in this loop
- **Transitions:** fade, horizontal slide, spatial (directional pan), with smooth easing; animated overview zoom in/out. An extension's `mdeck_sdk::transition::Transition` is `TransitionKind::Extension(name)` (`TransitionKind::parse` asks the registry); `render::transition::sides` (where each slide is drawn at a progress) and `paint_over` are shared by the window (`app/placement.rs`) and export (`--moment transition`), so both draw a change the same way. Names are validated by `language::Kind::Transition` and the theme build.
- **Designs:** `parser::design` holds the 13 designs (`Design`) and the one recognition table `RULES` (thresholds `SHORT_LINE_CHARS`, `STATEMENT_MAX_*`, `LEAD_MAX_CHARS`; `rules_reference` fills `<!-- generated: designs -->` in the spec, a test keeps `docs/writing-slides.md` in sync). `Slide::design` and `Slide::recognition` (why: rule, `design:` setting, rest in the body, fell back); `--check -v` prints it and `design_warnings` reports chosen designs that cannot hold the slide. `Slide::layout` / `parser::Layout` is only a coarse view for the engines' scenery until they read designs. How a design looks is an `Arrangement` (`theme/arrangement.rs`): the sets `crates/mdeck/designs/{standard,editorial}.yaml` (a `base` plus per-design keys), a theme's `designs:` and partial `arrangements:` (merged key by key, `all:` for every design), `spacing:` tokens and `radius`. `render::designs` is the one renderer: `parts::of` sorts blocks into copy, plate, footer and columns (every block lands somewhere), `plan` lays the slide out into pieces (`copy::Stack`) and plate items, `layout` fits it (short code grows toward `CODE_GROW_CEIL` of the body size; overflow shrinks visuals in the copy to `VISUAL_FIT_FLOOR` (`Lay::visual_fit`), code to `CODE_FIT_FLOOR`, then prose to `PROSE_FIT_FLOOR`) and `measure`, `revealed_bottom` and `render` all use that same plan. Seams for the engines: `theme::uses_editorial`, `render::design_has_stage` / `design_stage` (the arrangement's `stage`). `render::editorial` keeps only the chrome and compatibility questions engines ask. Never add a design-set branch in Rust: put it in the arrangement data. A `designs:` name no data set has may name a registered code `DesignSet` (`Theme::code_designs`, `Theme::code_design_set`): `render::render_slide` then draws through `render::board` (the board engines' path, with `measure` for scrolling), `--check` reports its `unsupported` (`check::engine::design_set_warnings`), and an unknown name falls back to `standard` with a warning. Unit tests see a test design set and transition (`registry::test_extensions`) next to the built-ins.
- **Scroll/overflow:** Per-slide smooth animated scroll with fade gradients; Up/Down keys; each slide's `SlideView` (`app/mod.rs`) holds its reveal step and a scroll offset eased toward `scroll_target`. Before scrolling, code and then prose shrink to fit (`render::designs::layout`); measurement is the drawing's own plan, so scroll detection always agrees.
- **Keyboard:** one shared table in `app/keys.rs` (`SHORTCUTS`, `map_key`) drives key handling, the HUD and `mdeck spec --short`; add new bindings there. Space/N/Right/PageDown/Enter forward, P/Left/PageUp/Backspace back, Up/Down scroll, Home/End, digits + Enter jump (`keys::SlideJump`), G grid, V presenter view, Shift+V reset its timer, T transition, Shift+T theme, F fullscreen, M next monitor, H HUD, `.`/B blackout, R debug overlay, Esc×2 / Q×2 / Ctrl+C×2 quit
- **End slide:** Virtual "The End" slide with MDeck logo shown when navigating past the last slide
- **Math:** `$...$` / `$$...$$` parse to `Inline::Math`. `render::math::append` lays the formula out with RaTeX (KaTeX fonts in `fonts/katex/`, one egui family each) and reserves its width in the text job with an invisible placeholder (word joiner + invisible id digits + an end char carrying the width as letter spacing); `render::math::galley`/`galley_tinted` paint a galley and then its formulas on the row's text baseline. Paint any galley that may hold markdown inlines through these helpers, never `painter.galley` directly: they also settle inline code chips on the prose baseline (`render::text::mono::settle`). Append code text with `text::append_code`, which splits sections between punctuation so the monospace font forms no ligatures.
- **Language and settings:** `crate::language` is the one table of every setting (`SETTINGS`: name, scope deck/slide/both, value kind, default, summary, since) and every mdeck fence (`FENCES`); `language::invalid_value` and `language::suggestion` validate, `settings_reference`/`settings_card` generate the tables in `mdeck spec` (the `<!-- generated: settings -->` marker in `mdeck-spec.md`) and `spec --short`. A new setting goes in that table, then the parser reads it. Deck settings are plain YAML keys (`parser::frontmatter`, every key kept in `meta.settings` with its line); slide settings are `key: value` lines in an HTML comment whose first key is known (`parser::settings::extract_settings`), applying to the slide they are in; read values with `parser::setting` (last wins, trimmed). Nothing moves between slides. v1 syntax (`@key:` lines, `@` frontmatter keys, `???`, renamed fence tags) is plain text or ignored, and `commands/check/settings.rs` names its v2 form. Until phase 3, `design:` maps onto the v1 `Layout` (`parser::layout::design_layout`), and `picture`/`picture-prompt` fill `Slide::illustration`/`Slide::art`. `Slide::line` and `Slide::source_lines` map a slide back to the file (`splitter::locate`) so `--check` warnings name their line.
- **Markdown model:** `parser::splitter` splits at headings (ATX and setext) at the slide level and at `---` breaks, never inside fences or HTML comments. Notes are ```` ```@notes ```` fences (`parser::notes`), joined per slide; footnote text joins them. Reference-link and footnote definitions are taken from the whole body first (`parser::references`, a thread-local the inline parser resolves against while a deck parses). Steps are numbered once per slide in reading order (`parser::steps::number`): `ListItem::step` per item (children of a `+` item share its step), `step_base` on every visual block (draw it with `BlockCx::after_steps(step_base)`); the deck renumbers with real thermal counts. Quotes hold blocks (`Block::BlockQuote { blocks }`, `Block::quote_parts` for quote and attribution), GitHub alerts are `Block::Callout`, lists carry their `start`, tables their `align`, task items `checked`.
- **Deck:** `crate::deck::Deck` is the deck as the window and export both hold it (presentation, `max_steps`, illustrations, art, logos, images, the engine `Host`); both draw through `Deck::engine_layer`, `Deck::draw_slide` and `Deck::draw_logo`, so export shows what the window shows. `deck_theme` and `deck_engine` resolve the theme and engine the same way for both.
- **Render contexts:** drawing takes a context instead of loose arguments: `render::TextCx` (ui, theme, opacity, scale), `render::BlockCx` (plus image cache and reveal) and `visualizations::VizCtx` for charts. `render_slide(cx, slide, rect, slide_cx)`; layouts are `render(cx, slide, rect)`. The renderer never reaches `app`, `commands`, `cli`, `config` or `deck` (a test in `render/mod.rs` checks); what it needs is handed in, e.g. `main` passes the config's routing weights to `diagram::set_routing_weights`.
- **Charts:** a fence like ```` ```@bar ```` parses to `Block::Chart { kind: parser::Chart, content, step_base }`; `parser::Chart` is a fence tag looked up in the registry (`Chart::from_info`), so an extension's visual is a fence tag like a built-in. Built-ins register in `render/visualizations/builtin.rs` as `mdeck_sdk::visual::Visual`s whose `draw` still uses egui through a bridge (`with_viz`, a 2.0 deferral); `visualizations::draw` / `draw_tag` dispatch through the registry and `check_tag` / `is_visual_tag` ask it too. Configured external visual programs (`extensions::external`) are fence tags as well (`Chart::is_external`), drawn from their cached PNG by `render/text/block.rs`. Shared helpers live in `render/visualizations/` submodules re-exported from `mod.rs` (`axis`, `values`, `legend`, `reveal`, `fit`, `frame`): `nice_grid_step`, `nice_axis_max`, `format_value`, `parse_value`, `sector_mesh`, `PlotFrame` for axis charts, and the legend helpers; reuse them instead of re-implementing per chart. Every visual (`@architecture` and `@thermal` too) reads its fence with `visualizations::grammar` (`Source::parse`: `key: value` settings before the first item, list items with `(key: value)` attributes and verbs as first word, `A -> B: label` relations, `#` comments) and reports what it cannot read through its `check`; `--check` shows them in category `visual` (`commands/check/visuals.rs`). A test parses every visual example in `mdeck-spec.md`
- **App structure:** `app/` is one `PresentationApp` split by concern: `frame.rs` (the frame loop: housekeeping, input, expiry, paint), `actions.rs` (keyboard actions, monitor hop), `navigation.rs`, `reload.rs`, `countdown.rs`, `opening.rs` (the window's first moment: black until macOS's fullscreen slide-in is over, when the window's position changes, then the deck fades in; the countdown's clock starts then), `grid.rs` (pure `GridLayout` geometry), `overview.rs`, `overlays.rs`, `end_slide.rs`, `launch.rs` (`run`, `RunOptions`), `look.rs` (theme, transition precedence deck > theme > config > `fade`, `slide_transition` for per-slide ones), `presenter/` (the presenter view: pure `layout`, `draw`; `presenter/notes.rs` the notes overlay and markdown notes via `notes_blocks`; export draws it with the hidden `--presenter-view`), `cockpit.rs` (the presenter window as an immediate egui viewport, its placement on the other display, the slide-jump digits). Chrome over a slide (footer, counter, editorial chrome) is `Deck::draw_chrome`, drawn by the window and export alike. The end slide is `AppMode::Presentation { end: true }`.
- **Diagrams:** Grid layout (when `pos:` specified) or auto-layout; geometric fallback icons; AI-generated icon images from `media/diagram-icons/`; 5 arrow types (`->`, `<-`, `<->`, `--`, `-->`)
- **Generated assets:** `crate::assets` is the one model for everything `mdeck ai` makes: `<deck>.assets/` with `manifest.yaml` (`assets::manifest`: `Kind::{Artwork, Image, Icon, PointCloud}`, `State::{Current, Stale, Pinned}`, artworks matched pinned > slide hash > slide number, placeholders by prompt then style), `assets::placeholders` (`![prompt](generate:)` and `icon: generate:` stay in the source; `Deck::open`/`replace` resolve them in memory through `assets::resolve_placeholders`) and `assets::style` (one style system: prompt plus reference images; `--style` > `@image-style`/`@icon-style` > config default > built-in; artworks use the medium's card in `render::art::style`). `commands/assets/` holds `mdeck ai images|icons|point-cloud <deck>` and bare `mdeck ai <deck>` (shared `cli::Select`: `--slide`, `--stale`, `--force`, `--dry-run`, chosen by `commands::assets::wanted`); `--check` category `assets` is `commands/check/assets.rs`.
- **AI integration:** `ailloy` crate for unified AI access (chat + image generation); config via `~/.config/ailloy/config.yaml`; async via `tokio` (`commands::util::block_on` runs a future from sync code). `commands::ai_reply` holds the shared reply handling: `strip_fence`, `json_object` and `chat_validated` (ask, check, ask once more with the error).
- FPS overlay in the top-right corner while the HUD (`H`) is shown
- **Themes are data:** `theme/` holds the schema and `extends` merge (`file.rs`), lookup deck `themes/` > user `themes/` > built-in (`lookup.rs`) and contrast advice (`validate.rs`); `Theme::build` (`theme/build/`) resolves a file section by section and fails with a `ThemeError`. Built-ins are `crates/mdeck/themes/*.yaml`, embedded in `lookup::BUILTIN`; add a theme there, not in Rust. Behaviour goes through the engine's capabilities (see Engines); never branch on a theme's name. Theme font files register via `render::fonts::register_file_face` (checked with skrifa first, since egui panics on a bad font) and are drawable one frame after `FontSync::sync`, so the app switches themes through `pending_theme`. Spec section 9.4 is also the prompt for `mdeck ai theme --from`. Logos: `render::logo::resolve_slides` resolves theme `logo:`, the deck's `logo` keys and each slide's `logo` once per deck (`Logos::get(slide)`) and draws in the app chrome and in export.
- **Config precedence:** frontmatter > the user config's defaults (`config.yaml` in `dirs::config_dir()/mdeck/`: `~/.config/mdeck/` on Linux, `~/Library/Application Support/mdeck/` on macOS) > built-in (theme, start mode); the theme is `--theme` > `theme` > config; the transition is deck `transition` > theme `transition:` > config > `fade`; the countdown is deck `countdown` > theme `countdown: on|off` (the engine decides its look); the engine is `--engine` > `engine` > the theme's
- **Library and registry:** `crates/mdeck` is a library plus a thin binary: `mdeck::builtins(&mut Registry)` registers the built-in engines, visuals, themes and point clouds, `mdeck::run(registry)` (or `run_with_args`) runs the CLI; `src/main.rs` is those two calls and `mdeck build` generates the same with extensions. `crate::registry::get()` is the registry in use (installed by `run`, else built-ins only). Engines (`EngineId`), visuals (`parser::Chart`), embedded themes (`theme::lookup::builtin_file`) and embedded point clouds (`render::point_cloud`) resolve through it; `Registry::registrations` feeds `mdeck extensions list`. Unknown names fall back (engine to plain, fence to code) and `--check` reports them. `tests/extension_engine.rs` exports a slide with `examples/engine-ambience` registered next to the built-ins.
- **Engines:** `src/engines/`: `plain`, `particles`, `led`, `splitflap` (a `board` engine: its `DEF.board` design set draws every slide, `render::board::render` calls it; `Capabilities.transition` makes the core do no slide motion), `blocks`, `thermal` (heat field; settings `palette`, `drift`; the cold opening through `Engine::copy_hold` and `Hint::Text`; the heat trace through `Engine::annotate`), and the art engines `line` (setting `surface: sheet|slate`; `numbers_slides` on the sheet), `sketch`, `watercolour`, `darkroom` (see Art engines), each a cargo feature with a showcase theme. **Every engine is written against `mdeck-sdk` only** (`mdeck_sdk::engine::{Engine, EngineDef}`, drawing through `mdeck_sdk::paint::Painter`, sprites through `SpriteLayer`); a test keeps everything under `engines/` except `engines/host/` to `mdeck_sdk` and `crate::engines::` helpers, no egui. Capabilities are `picture`, `countdown`, `ending`, `board`, `transition`, `medium`; branch on them, never on an engine's or theme's name. `engines::register` registers the built-ins; `EngineId` is the registered def a theme carries (`Theme::set_engine` also learns `copy_hold` and `numbers_slides` from a runtime made with the theme's settings). `engines::host` is the core's half the app and export own: it converts the parsed slide to the SDK content model (`host::convert`), the theme to `Tokens` and font roles, published hints to SDK `Hint`s, resolves the picture (D13: artwork on art engines > named point cloud > named image file, the last two only where `render::design_has_stage`), times the end slide, draws the countdown and end masks, and builds `Stage`/`Frame`/`Painter` each frame. Engine settings come from the theme's `engine:` block through `theme::engine_settings` (minus `theme::CORE_ENGINE_KEYS`, the tints and art keys the core reads); `engines::settings_problems` reports bad values in `--check` and `theme check`, `theme::validate::engine_keys` (the def's `settings` plus the core keys) drives `inert` and the starter theme. Where pictures go is the design's: `render::design_has_stage` / `design_stage`; the SDK slide's `design` is the v2 design name. `--engine` > `engine` > theme `engine:` via `engines::choose` and `with_engine`; `engines::unsupported` feeds the `engine` check category and the startup summary. Adding one: `crates/mdeck/doc/engines.md` and `docs/sdk/`. `mdeck export --at <seconds>` / `--moment countdown|end` export stills of motion (`commands/export/rehearsal.rs`); `scripts/engine-golden.sh` proves a change did not move other engines. `src/guards.rs` tests that `build.rs`'s `ENGINES`, the cargo features and the CI engine matrix name the same engines, and that each has a showcase theme and a `samples/engines/` deck.
- **Particles engine field:** `engines/particles/` owns one `Field` (`field/`, `scene.rs`, `scenes/`); each frame it picks a scene from the stage (countdown digit, end act, the picture's point cloud, the geometry visuals published, or the scene inferred from `slide.design`), ticks it and paints it with an SDK `SpriteLayer` (`AdditiveWakes` live, `Additive` for stills, `Normal` on light themes). Backdrops and formations (`scenes::backdrop`, `scenes::formation_points`) rotate by slide number so neighbours differ and exports stay reproducible. Renderers publish geometry with `render::hints::push` (a no-op unless an engine is drawing).
- **Art engines:** `render::art` is the core's pipeline for engines that draw a picture generated per slide (`Capabilities.medium`, mapped to its style card by `render::art::Medium::of`). `style.rs` holds the style cards (prompt + bundled swatches in `crates/mdeck/art/<card>/`; line art is one card shared by every line medium) and a theme's `art:` block overrides them; `resolve.rs` reads the deck's asset manifest for artworks; `prepare.rs` trims, keys out the paper and lays out the per-pixel time map into an `mdeck_sdk::stage::Artwork`; `gallery::DeckArt` resolves and loads (a worker pool in the app, inline in export). The engines' side is `engines/art/`: `Canvas`, `Drawing` (CPU reveal, `reveal.rs`, into a texture), pen `strokes.rs` and `fallback_strokes`. `mdeck ai pictures` and the `S` key live in `commands/art/`. Presenting never calls the AI.
- **Thermal images:** a ```` ```@thermal ```` block (`Chart::Thermal`) is drawn by `render::thermal::draw` with the full `BlockCx` (it needs the image cache), never by `visualizations::draw`. `thermal/spec.rs` parses the block (keys, `lens`/`reveal`/`above`/`spot` steps, `Support` decides which steps a source keeps so no click is dead), `source.rs` reads sources (display image, `mapping: linear`, or `data:` 16-bit PNG + `.yaml` sidecar; values kept apart from textures, colour input detected by pixel tolerance), `library.rs` loads every source when the deck opens (`ImageCache::thermal_mut().load`, so step counts and diagnostics are known up front; `Deck` counts thermal steps through it) and caches composed textures per look, `state.rs` is the reveal state as a pure function of the step, `compose.rs` the palette/window/threshold/hatching pass, `palette.rs` the LUTs. The live palette (`C`) and the deck's `palette` reach blocks through egui context data (`set_live_palette`, `set_deck_palette`); a slide's `thermal-window` is appended to its blocks as `slide-window:` by the parser. Spots remember where they were drawn (`spot_anchor`) for the `zoom-to` transition (`render::transition::Zoom`, resolved in `app::drawing::resolve_zoom`). `--check` category `thermal` reuses `Library::load`'s diagnostics.
- **Extension tooling:** `commands/sdk.rs` (`mdeck sdk new`, templates embedded in the SDK as `mdeck_sdk::templates`), `commands/build.rs` (`mdeck build`: generated cargo project in `<cache>/mdeck/build/<hash>/` calling `mdeck::builtins` and each extension's `register`, then `mdeck::run`), `commands/pack.rs` and `commands/extensions.rs`; their clap types live in `cli/extend.rs`. Runtime halves are in `src/extensions/`: `packs` (manifest, install, `theme_dirs` / `point_cloud_dirs` / `dirs_for` in lookup order deck packs then user packs; `styles` reads `styles/*.yaml` into `Config::pack_styles` via `Config::with_packs`, the user's own styles win; `pack_of` finds a pack theme's `fonts/`; design sets in `designs/` folders resolve through `Lookup::designs` and `Arrangements::resolve_in`), `external` (EXT-18 programs from config `visuals:`, PNG on stdout, cached in `<stem>.assets/visuals/`; `configure` from `run`, `prepare_deck` at deck open, `draw` in the block renderer) and `provided()` (the registry's registrations with origins). `requires:` is checked in `commands/check/requires.rs`.
- **Reduced motion:** `--reduced-motion` / `defaults.reduced_motion` make the app show settled states: `TransitionKind::None` (`transition_kind`), no reveal timestamps, `SlideContext::animate` false, engine frames `still`, no countdown.
- **Page:** a theme's `page:` block makes the slide a sheet on a surface; `render::page::draw` paints it and returns the sheet rect, which the app and export then use as the slide rect for everything (engine layer included).
- **Point clouds:** `render::point_cloud` owns the `.mdpc` format (`Cloud`, importance-ordered points, `aspect` = height/width), the lookup order (deck `<deck>.assets/point-clouds/` > deck `point-clouds/` > the user config folder's `point-clouds/` > packs > `BUILTIN`; a v1 `illustrations/` folder is only reported by `--check`), and the per-deck `Library` cache the app, export and check pass into `engines::Host::frame`. `convert.rs` turns an image into points: composite over black, dilate dots into strokes, threshold, greedy farthest-point ordering weighted toward silhouette edges. `Home::Mask` takes the first *n* points for a group of *n* particles, so glyph masks are shuffled once when built. Placement: `scenes::illustration_stage` (copy slides) and `scenes::illustration_backdrop` (title slides); only designs with a stage show one (`render::design_has_stage`). Built-ins live in `crates/mdeck/point-clouds/`; `build.rs` registers every `.mdpc` there (no source change needed to add one). To promote generated clouds to built-ins use the [`/include-point-clouds`](.claude/skills/include-point-clouds/SKILL.md) skill; to regenerate, run `mdeck ai point-cloud --name ... --description ...` from `crates/mdeck/`.

## Reported issues

GitHub issues are handled with the [`/fix-issue`](.claude/skills/fix-issue/SKILL.md) skill: read and classify the report, reproduce a bug before fixing it, ask the reporter when the report is not reproducible, fix with test, sample and changelog, then thank the reporter in a closing comment that shows before/after screenshots (published to the `issue-screenshots` branch by the skill's `upload-screenshot.sh`) before the issue is closed. Commits reference the issue as `(#n)` and never use closing keywords.

## Releasing

Releases are driven by the [`/release`](.claude/skills/release/SKILL.md) skill (`major`, `minor`, or `patch`): it runs the pre-flight checks, bumps `version` in the root `Cargo.toml`, renames `[Unreleased]` in `CHANGELOG.md` to the dated version, commits `Release vX.Y.Z`, pushes main, and pushes the tag `vX.Y.Z`.

## Code Style

- Building from source on Windows needs NASM and CMake on `PATH`: `aws-lc-rs` (the TLS crypto
  backend pulled in transitively via `ailloy`) compiles optimized assembly routines at build time.
  macOS and Linux need nothing extra. The release workflow's Windows leg installs NASM with Chocolatey; CMake and MSVC are
  already on the `windows-latest` image. Its Linux leg builds on a pinned `ubuntu-24.04`
  (not `ubuntu-latest`) so the binary's glibc requirement stays low.
- **File size guideline:** When a source file exceeds ~500 lines, evaluate whether it would benefit from being split into smaller modules (`mod` in Rust). Look for natural boundaries: distinct type groups, self-contained algorithms, test helpers, or feature areas that could live in their own files. Propose a split plan before refactoring.

## Dependency Policy

We keep this tool's dependencies at their latest compatible versions, not just the versions that
happen to still compile. Staying current is the default, not something we get to eventually:
letting dependencies drift is how technical debt accumulates unnoticed until a security advisory or
a forced breaking upgrade makes it urgent. When a newer major is available and there's no concrete,
documented reason not to take it (see any `# Stays on ...` comments in `Cargo.toml` for the current
exceptions and why), take it during the next maintenance round rather than deferring it. The
cross-repo `maintaining-rust-tools` skill drives this for the whole fleet (ailloy + cosq + deemer +
mdeck + pidge + rigg + rusty-tmpl).

## Quality Requirements

### Testing
- **Always run the full test suite before declaring work complete:** `cargo test --workspace`
- **Always run the full CI check before pushing:** `cargo fmt --all -- --check && cargo clippy --workspace -- -D warnings && cargo test --workspace`
- Write unit tests for all new functionality
- Test edge cases and error paths, not just the happy path
- **Every bug fix must include a regression test.** When fixing a bug, first write a test that reproduces it (fails before the fix, passes after). This prevents the bug from coming back and documents the expected behavior.
- When fixing incorrect tests, explain why the original assertion was wrong before updating it

### Visual Testing
- **Always verify rendering changes visually before declaring work complete.** Use the export command to generate slide PNGs and inspect them:
  ```bash
  cargo run -p mdeck -- export samples/layouts/code.md --output-dir /tmp/slides
  ```
  Then read the exported PNGs to check layout, syntax highlighting, spacing, and overall visual quality.
  To check one slide without rendering the whole deck, add `--slide N` (and `--debug` for its reveal steps).
- Per-feature test decks live in `samples/visualizations/`, `samples/layouts/`, `samples/transitions/`, `samples/features/`, `samples/ember/` and `samples/themes/` (custom themes and logos; `samples/design-systems/` is the input for `mdeck ai theme --from`); `samples/visualizations/all.md` has every visualization type. When working on a specific visualization type, use its dedicated test file for faster iteration.
- When fixing visual issues, export before and after to confirm the fix.

### Runtime Testing
- **After making changes, run the application and check for runtime incidents.** Launch a relevant test presentation, navigate through slides, then check for errors:
  ```bash
  cargo run -p mdeck -- samples/visualizations/all.md
  ```
  After quitting, if the application reports incidents, read the log file and fix any issues. Incident logs are at `~/Library/Application Support/mdeck/logs/` (macOS) or `~/.config/mdeck/logs/` (Linux).
- Common issues to watch for: `time_jump` false positives (threshold must exceed the repaint heartbeat interval), rendering panics, and layout overflow.
